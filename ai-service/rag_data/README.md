# rag_data —— RAG 语料库（离线知识源）

> 本目录是 `app/rag/ingest.py` 的输入。
> **这不是给人读的普通文档，是给机器检索的"事实单元集合"。** 所以写法有硬性约束，见下文。

---

## 1. 为什么语料要单独放一个目录

三条理由，缺一条都会让 RAG 效果变差：

1. **可 diff / 可 review**：规则改动进版本库，能对比、能回滚。规则写在数据库里改了什么你查不到。
2. **可离线重跑**：语料变了 → 重新跑 `ingest`，不用改代码。
3. **和商品数据分开**：商品来自 MySQL/ES（实时、结构化），规则来自本目录（静态、长文本）。**两类语料的切分策略是相反的**，混在一起必然有一类受损。

---

## 2. 目录与 source 的对应关系

`source` 字段是检索时**选择召回通路**的依据，必须严格按目录来：

| 目录 | source 值 | 语料性质 | 切分策略 |
|---|---|---|---|
| `platform/` | `policy` | 平台规则、交易/售后条款 | 按 `##` 条款切，**一个条款必须完整落在一个 chunk 里** |
| `faq/` | `faq` | 问答对 | 按 `##` 切，**一问一答必须完整**（问题+答案不能被拆开） |
| `guides/` | `guide` | 运营/材质/保养知识 | 按 `##` 小节切，chunk 前**冗余带上文件标题 + 小节标题** |
| `products/`（不在此目录） | `product` | 商品数据 | 来自 MySQL/ES，**一品一 chunk，绝不切分** |

> 🔴 **绝对不放进来**：`t_user`（手机号/邮箱/密码）、`t_order`、`t_account`、`t_transaction`、未上架商品。
> 向量库没有行级权限，一旦入库 = 全局可检索 = **数据越权**，比幻觉严重一个数量级。
> 订单/账户类问题一律走**工具调用**（带 token 实时查）。

## 3. 文件格式约定（ingest 依赖这个约定解析）

### 3.1 文件级元信息：YAML front matter（零依赖的 `key: value`）

每个文件**第一行必须是 `---`，紧接着是元信息，再一行 `---` 收尾**：

```markdown
---
docId: policy-refund
source: policy
title: 退换货与退款规则
url: /help/policy/refund
updatedAt: 2026-09-14
version: 1
---

## 退换货适用范围
...
```

字段说明：

| 字段 | 必填 | 用途 | 缺失后果 |
|---|---|---|---|
| `docId` | ✅ | chunk 唯一标识前缀（实际 `_id` = `docId` + 小节序号） | 无法做幂等 upsert，重复入库灌水 |
| `source` | ✅ | 决定走哪条召回通路 + 硬过滤 | 检索路由失效 |
| `title` | ✅ | 给模型判断相关性 + 给用户看引用来源 | 引用不可读 |
| `url` | ✅ | 🔴 **让用户能点进去核对 → 幻觉伤害大幅降低** | 用户无法核对 |
| `updatedAt` | ✅ | 时效过滤（政策类必须能剔除过期文档） | **最常被漏掉的一个** |
| `version` | 🟡 | 增量更新时判断新旧 | 旧文档覆盖新文档 |

> 解析建议：不要为此引入 pyyaml。按行 split `:` 取前两段即可（约定里不许出现嵌套结构）。

### 3.2 切分边界：`##` 是唯一的 chunk 边界

- `#` 一级标题 = 文件标题（**不作为 chunk 边界**，但会被冗余拼进每个 chunk 的上下文前缀）
- `##` = **一个 chunk**（一个条款 / 一组问答 / 一个小节）
- `###` = chunk 内部的层级（跟着父 chunk 一起走）

🔴 **约束**：写完每个 `##` 后自查一句 —— **"单独看这一块，能不能自证它在讲什么？"**
不能，就说明它脱离上下文后无法被检索到。两条修法，选一条：
- 补全主语（把"定制商品除外"写成"退换货规则的例外情况：定制商品除外"）
- 依赖 ingest 的 `enrich_with_context()` 自动补"文件标题 + 小节标题"前缀

### 3.3 语言风格

- **陈述句、无歧义、可被逐字引用**。检索出来的内容会直接进 prompt，模型会照着说。
- 🔴 **禁止**："大概"、"可能"、"建议咨询客服"（除非确实只能咨询客服，且要写清咨询入口）。
- 🔴 **禁止**："详情请见页面"这类无信息量的句子 —— 它占了 chunk 却不提供事实。
- ✅ **推荐**：把时间、金额、次数这类**可被答后校验**的硬数字写清楚（"48 小时"、"_7 天_"、"≤ 200 元"）。
  答后数值校验（`core/guardrails.py`）就是靠这些数字和答案做比对的，语料里没有数字，校验层就无从下手。

## 5. 🔴 交付前你需要确认的参数（这些是业务决策，不是技术问题）

文档里凡是标了 `> 🟡 待确认` 的，都是**我按行业通例写的默认值**。
它们是**会进入用户回答的硬数字**，必须由你（平台方）确认或改写，否则 AI 会照着"猜的规则"回答用户 —— 这比说"不知道"更糟。

清单一览（建议一次性定稿）：

| 项 | 当前默认值 | 你的确认值 |
|---|---|---|
| 卖家发货时效 | 付款后 48 小时内 | |
| 自动确认收货 | 发货后 10 天 | |
| 超时未支付关单 | 30 分钟 | |
| 无理由退货期 | 签收后 7 天 | |
| 定制商品是否支持无理由退货 | 不支持（法定例外） | |
| 退款到账时长 | 1~3 个工作日 | |
| 包邮门槛 | 满 99 元 | |
| 平台佣金 | 成交额 5% | |
| 信用分初始值 / 封禁阈值 | 100 / 低于 60 | |
| 内容审核时效（商品上架） | 24 小时内 | |

## 6. 验收（照 `ingest.py` 的标准执行）

- [ ] 连续跑两次 `ingest`，向量库文档数**不变**（幂等）
- [ ] 抽 10 个 chunk 人工检查：**语义完整、metadata 齐全、无敏感数据**
- [ ] 用 3 个已知问题测检索，正确答案**能在 Top5 里被召回**
- [ ] `Recall@5` 打印出来。**不达标就先别写 Agent**
